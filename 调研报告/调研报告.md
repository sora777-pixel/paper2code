## 1.3 关键差距分析

把需求当成一个「**单一入口 → 两类产出 → 三种情形分派**」的系统来看，现有项目在四个维度上都有断层：

**差距一：讲解与复现被割裂成两条互不相通的产品线。**
课件侧（Auto-Slides、SlideGen、paper2slides）和播客侧（podcastfy、papercast、Talking Agents）各自独立，
没有任何一个项目同时产出"课件 + 播客"。而"复现"又完全是另一个社区（PaperBench、PaperCoder、SciReplicate）。
需求要求的是**同一篇论文的两类产出共享同一份结构化理解**（同一份抽取结果既喂给课件，也喂给复现）——
这一点没有任何现成项目做到。

**差距二：复现的目标错位 —— 大家都在"生成代码"，很少人在"重现表格数字"。**
PaperCoder、AutoP2C 的产物是一个**新的代码仓库**；PaperBench 是**评测基准**不是工具；
Sci-Reproducer 只覆盖"单函数级算法"。而需求要的是**论文里那张表、那张图，被重新算出来**，
并给出可对照的判定。只有 THU-Digitizer / CopyPlot / NaturePanelForge 触及"图级重现"，
但它们是**从图片逆向取数**，而本需求的数据源是**论文表格与附带数据文件** —— 前提不同。

**差距三：三种情形没有统一入口，且没人做"情形分派"。**
逐条看：PaperCoder/AutoP2C 面向"无代码"；ToolMaker、42-checker 面向"有代码"；
SciReplicate 面向"算法描述"。**没有任何项目把这三者作为同一入口下的分派策略**，
更没有哪个工具会**先判定论文属于哪一类、再据此选择复现深度**。
而这恰恰是需求的核心：三种情形的复现**目标本身就不一样**（指标对标 / 逻辑等价 / 数据自洽），
不能用同一把尺子去量。

**差距四：没人显式区分"逻辑复现"与"指标复现"。**
SciReplicate 报的是执行准确率（39%），PaperBench 报的是 rubric 得分（21.0%）。
这些指标隐含了"跑通≈复现"的假设。但一个只给了伪代码的论文，
**逻辑跑通与指标一致是两件完全不同的事**，报告里必须分开声明。现有工具不处理这个区分。

## 1.4 调研结论

> **结论：没有现成项目可以直接满足需求；但需求中约 70% 的子能力有成熟开源件可复用。**
> 需要自建的只是"编排层 + 三情形分派 + 表格数值逐格对标"这一小部分，而不是从零造轮子。

具体地：

1. **不存在**任何一个开源项目同时提供「课件 + 播客 + 表格图表复现」，且按三种情形分派策略 ——
   因此**必须自建编排层**，无法通过 fork 单一项目完成。
2. **讲解材料**可直接站在成熟件上：播客路径可复用 `podcastfy` 的架构与 `edge-tts` 引擎；
   课件路径可借鉴 `Auto-Slides` 的"生成 → 校验 → 修复"流程与 `SlideGen` 的多 agent 分工。
3. **复现路径**没有成品可复用，必须自研；但其中的文档解析（`MinerU`/`Marker`/`Docling`）、
   图表渲染（`matplotlib`）、图逆向思想（`THU-Digitizer`/`CopyPlot`）都可复用或借鉴。
4. **真正需要从零实现的只有三块**：
   ①「论文 → 结构化对象」的统一摄取契约（含"论文包"约定）；
   ②「三情形判定 + 差异化复现策略」；
   ③「复现产物 ↔ 论文表格的逐格对标与分级判定」。
   这三块正好构成本项目的最小自研内核，也是它相对现有工具的差异化所在。

**落地上的一条重要判断：** 需求中"输入数据来源于论文中提及或附带的数据"这句话，
决定了整个系统的架构重心在**摄取与数据重建**，而不在"生成模型代码"。
这也是为什么不采用 PaperCoder 那种"重写一个仓库"的路线 —— 在单机、<1 万条记录的约束下，
那条路线既不可控（LLM 生成仓库的调试成本极高），也偏离了"重现表格数字"的目标。

# 第二部分 · 模块拆解与复用方案

## 2.1 模块分解总览

按"数据流 + 职责单一"拆成 12 个模块，分属四个层次：

```
┌──────────────────────────────────────────────────────────────────┐
│  编排层   M12 编排与产物规范 / CLI / Web UI                        │
├──────────────────────────────────────────────────────────────────┤
│  能力层   M4 课件   M5 播客   M7 复现A   M8 复现C   M9 复现B       │
│           M6 TTS              M10 执行沙箱                          │
├──────────────────────────────────────────────────────────────────┤
│  决策层   M3 情形判定（三情形分派）                                │
├──────────────────────────────────────────────────────────────────┤
│  基础层   M1 论文摄取   M2 内容抽取   M11 LLM 抽象与降级            │
└──────────────────────────────────────────────────────────────────┘
```

## 2.2 逐模块选型与理由

### M1 论文摄取与结构化

| 项 | 内容 |
| --- | --- |
| 职责 | PDF / Markdown / HTML / arXiv → 统一的 `Paper` 领域对象（标题、作者、摘要、分节、表、图、算法块、资源链接） |
| 复用方案 | **直接复用**：PyMuPDF（正文+图像）、pdfplumber（表格）；**可选后端**：MinerU / Marker / Docling（高精度，含公式）；**自研**：统一领域模型 + "论文包"目录约定 |
| 选型理由 | 基准数据显示 MinerU 在 OmniDocBench 的 Overall Edit 为 0.15（EN）/ 0.357（ZH），是流水线类工具中最优，但它要下载 1.2B 参数模型、对内存要求高（Auto-Slides 用 marker-pdf 时提示需 ~8GB RAM），与"单机小数据"的约束冲突。因此把它设计成**可选后端**，默认链路用 PyMuPDF + pdfplumber，并保证 Markdown/HTML 链路**零第三方依赖**即可跑通 |
| 备选与取舍 | 放弃 Nougat：中文支持弱、易幻觉；放弃 GROBID/Science-Parse：只抽元数据与参考文献，不解决表格数值抽取 |


**Bakeoff 2026-09-14（schnorb_qao_2020）：** 对同一 PDF 对比 Docling 2.126.0 / Marker / PyMuPDF。Docling 标题、章节、TABLE I 单元格网格质量最好，但有约 34 处 formula-not-decoded（无 LaTeX）；Marker 在无 llama-server 时 OCR/公式不可用故跳过。因此本项目将 Docling 作为可选结构后端（hybrid：Docling 结构 + PyMuPDF 公式），Docling 留在 bakeoff venv 子进程，不装入 paper2code .venv。Marker / MinerU 未接线。

### M2 内容抽取（表 / 图 / 算法块 / 资源链接）

| 项 | 内容 |
| --- | --- |
| 职责 | 从正文中定位 Markdown/HTML/PDF 表格、图题与图片、伪代码块、代码仓库链接与数据集链接 |
| 复用方案 | 表格抽取复用 pdfplumber；**其余自研**（约 400 行规则） |
| 选型理由 | 调研中**没有任何库**提供"判断一段 fenced block 是伪代码还是真代码"、"判断一个 URL 是代码仓库还是数据集"的能力。而这两个判断正是 M3 三情形判定的输入，必须**可控、可解释** —— 因为判定结论要作为证据写进复现报告，供人工复核。用规则而非模型，是为了让每一条判定都能追溯到具体文本行 |
| 关键实现 | 伪代码判定：信息串含 `algorithm/pseudo`，或块内命中 ≥2 个算法关键字且不含 `def/import/class`；资源链接分类：按所在行上下文关键词 + 域名白名单 |

### M3 情形判定（三情形分派）· **完全自研**

| 项 | 内容 |
| --- | --- |
| 职责 | 判定论文属于「A 有开源代码 / C 仅伪代码 / B 无代码」，并输出判定依据与置信度 |
| 复用方案 | **完全自研**。调研中没有项目做这件事 |
| 判定优先级 | **A > C > B**。只要发现仓库链接（或论文包内附带 `code/`），即使论文里也有伪代码，也走情形 A —— 因为**复用仓库永远优于重新实现** |
| 选型理由 | 这是需求的核心差异化。调研结论（差距三）已说明：现有项目各自只覆盖一种情形，且没有分派逻辑。必须自研 |
| 输出形态 | `ModeDecision{mode, confidence, reason, evidence[]}`，`evidence` 会原样写入复现报告，保证可追溯 |

### M4 讲解材料 · 课件

| 项 | 内容 |
| --- | --- |
| 复用方案 | **借鉴** Auto-Slides 的"生成→校验→修复"多智能体流程、SlideGen 的 6-agent 分工（Outliner/Mapper/Arranger…）、paper2slides 的 Beamer 路线；**自研** HTML 渲染器 + 复用 LLM 生成大纲与要点 |
| 选型理由 | 三条候选路线各有权衡：① **Beamer（paper2slides）** 需要本地 `pdflatex`，Windows 单机环境部署成本高；② **PPTX（SlideGen）** 需要 `python-pptx` + LibreOffice 做渲染校验，链路长；③ **自包含 HTML** 双击即可放映、可打印成 PDF 讲义、零外部依赖。在"单机 MVP + 用户偏好卡片式/渐变/响应式 UI"的前提下，③ 的最短路径最优 |
| 扩展预留 | 渲染层与内容层解耦：`Slide` 对象与渲染器无关，后续加 PPTX 导出只需新增一个 `render_pptx(slides)`，内容生成逻辑不动 |


**课件 UX（2026-09-14 落地）：** 宽表外包横向滚动，首列 sticky；图/表点击 lightbox 放大；幻灯片内容区 `max-height` 内部滚动，避免溢出 PPT 框。详见第 4 节。

### M5 讲解材料 · 知识播客

| 项 | 内容 |
| --- | --- |
| 复用方案 | **直接复用** `podcastfy`（多源→双人音频，Apache-2.0，支持 edge-tts 后端）作为架构参照与备选底座；**自研**对白生成层 |
| 选型理由 | podcastfy 是这一格最成熟的成品，`pip install podcastfy` 即可用，理论上可直接接入。但它面向**通用内容**做播客，对白不可控。而本需求的播客必须**引用论文的具体数字**（例如"表 2 里 Ours 的 Accuracy 是 78.3"），所以对白层必须自研：由 `LLMProvider.dialogue()` 基于论文结构化对象生成，并把表格解读注入对白 |
| 许可证提示 | podcastfy 的许可证在历史版本间有变化（曾为 CC-BY-NC-SA 4.0，当前 LICENSE 为 Apache-2.0）。**若商用，请以仓库当前 LICENSE 为准并自行复核**。本 MVP 只复用其"思路"与底层 `edge-tts`，不引入其代码，因此不受该许可约束 |


**播客稿（2026-09-14）：** 全中文写作导读，覆盖研究目的 / 思路 / 方法 / 结论与不足；**不讲**公式与图表细节。TTS 走 SiliconFlow `POST /v1/audio/speech`，主推 CosyVoice2-0.5B 与 MOSS-TTSD-v0.5；无 Key 时回落 edge-tts。详见同目录 `SiliconFlow-TTS模型.md` 与第 4 节。

### M6 语音合成

| 项 | 内容 |
| --- | --- |
| 复用方案 | **主推** SiliconFlow TTS（`POST /v1/audio/speech`，OpenAI 兼容）；**兜底** `edge-tts`（免费、免 Key） |
| 选型理由 | Dashboard 可配 SiliconFlow Key；主推 `FunAudioLLM/CosyVoice2-0.5B`（单人）与 `fnlp/MOSS-TTSD-v0.5`（双人 `[S1]`/`[S2]`）。无 Key 时 edge-tts 兜底。设计成可插拔：`TTSEngine` 抽象 + SiliconFlow / edge-tts / Null 降级 |
| 降级策略 | 无网络时仍产出**播客脚本 + SRT 字幕**，并在产物 `warnings` 中明确说明未生成音频的原因，绝不静默失败 |

### M7 复现 · 情形 A（有开源代码）

| 项 | 内容 |
| --- | --- |
| 职责 | 复用既有仓库，把它的产出与论文表格**逐格对标** |
| 复用方案 | 复用 `git` 浅克隆、Python `venv` 隔离；**借鉴** ToolMaker 的"装依赖 + 闭环调试"思路、42-checker 的"论文↔仓库一致性"思路；**自研**仓库静态扫描、复现脚本生成、结果键对齐与逐格对标 |
| 选型理由 | 现有工具**没有一个是"跑既有仓库并做数值对标"的成品**：PaperCoder/AutoP2C 是"生成新仓库"，ToolMaker 是"把仓库包装成 LLM 工具"，42-checker 是"检查一致性不做对标"。因此这一格必须自研，但自研量不大（复用 git/venv，核心只是扫描 + 对齐） |
| 关键设计 | 仓库扫描只做**静态分析**（入口脚本、依赖声明、数据文件、结果文件），不重写论文方法 —— 这是"复用优先于重写"原则的具体落实 |

### M8 复现 · 情形 C（仅含伪代码）

| 项 | 内容 |
| --- | --- |
| 职责 | 伪代码 → 可执行 Python → 小规模执行 → **性质校验** |
| 复用方案 | **借鉴** Sci-Reproducer 的"Paper Agent 理解 + Code Agent 实现"双智能体分工；**自研**离线规则翻译器 + **伪代码原语 shim**（`push/pop/size/sort_descending/empty min-heap`…）+ 算法性质校验库 |
| 选型理由 | 伪代码里的 `push(heap, x)`、`empty min-heap`、`sort_descending()` 在 Python 里并不存在。与其把它们当错误，不如在生成代码的骨架里**注入一层薄适配**——这是"让伪代码真的跑起来"的关键工程细节。性质校验（有序性、Top-K 正确性、归一化守恒、排序排列不变性）则是对"逻辑复现"的可证伪表达 |
| 明确边界 | 本情形**只声明逻辑等价，不声称复现了论文指标**。报告与课件都会显式标注这一局限 |

### M9 复现 · 情形 B（无任何代码）

| 项 | 内容 |
| --- | --- |
| 职责 | 以论文表格 + 附带数据为输入，重建 tidy 数据 → 内部一致性校验 + 图表重绘 |
| 复用方案 | **借鉴** THU-Digitizer 的"证据优先、可审计"、CopyPlot / NaturePanelForge 的图风格复刻；复用 `matplotlib` 渲染；**自研**内部一致性校验库与缺失要素清单 |
| 选型理由 | 图逆向工具（THU-Digitizer / CopyPlot）解决的是"**从图片里把数抠出来**"，而本需求的输入是**论文表格与附带文件**（比图片可靠得多），因此不用图逆向，而是直接解析表格。重点转为两个现有工具都不做的事：**① 论文自身数据是否自洽**（占比列是否求和为 1、汇总行是否等于明细聚合、标称最优是否确实最优、排名列是否为合法排列）；**② 未披露要素清单**（数据集、超参、种子、预处理、硬件） |

## 2.4 规模约束与扩展性设计

需求要求"单机 + <1 万条记录，但架构需为更大算力留口"。落地为四条设计：

| 设计 | 实现 | 扩展时怎么改 |
| --- | --- | --- |
| **规模显式化** | `max_records=10000` 写入配置，并**写进每一份 `repro_plan.json` 的 `scale_guard`**；超限时确定性采样并**在报告中声明**，绝不静默丢数据 | 调大 `max_records`；或让调度器读取 `scale_guard` 后决定是否分发到集群 |
| **执行器可替换** | 所有代码执行收敛到 `runner.run_python_script()` 一个函数 | 新增 `run_docker()` / `run_slurm()` 并切换，计划与校验逻辑零改动 |
| **计划与执行解耦** | `repro_plan.json` 是纯数据（目标清单、输入、步骤、守卫阈值），不依赖任何执行细节 | 计划可直接作为作业描述提交给外部编排系统 |
| **数据规模无关的计算** | 表格校验、性质校验都是 O(n) 单遍扫描，n 上限 1 万时毫秒级完成 | 换成分块/并行实现即可，接口不变 |

## 3.3 三种情形的差异 —— 实现对照

这是需求最核心的部分。三种情形在**判定依据、复现目标、校验方式、产出深度**上全部不同：

| 维度 | A 有开源代码 | C 仅含伪代码 | B 无任何代码 |
| --- | --- | --- | --- |
| **判定依据** | 正文 GitHub 链接，或论文包内 `code/` | 有算法块，无仓库链接 | 两者皆无 |
| **复现目标** | **指标复现**：仓库产出 vs 论文报告值 | **逻辑复现**：算法行为是否等价 | **数据自洽性复现**：论文数据是否自洽 |
| **输入数据** | 仓库自带数据文件 | 按论文描述规模**合成**的小数据（≤1 万条） | 论文表格 + 附带数据文件 |
| **核心动作** | 静态扫描 → 生成隔离复现脚本 → 采集产物 → 逐格对标 | 伪代码 → Python 翻译 → 执行 → 性质校验 | tidy 化 → 一致性校验 → 图表重绘 |
| **校验方法** | 相对误差分级（≤5% pass / ≤20% warn / 否则 fail） | 算法性质（有序性、Top-K 正确性、归一化守恒、排列不变性） | 占比求和、汇总行、最优性声明、排名合法性、计数非负 |
| **复现深度声明** | "指标级一致" | **显式声明：仅逻辑等价，不对标指标** | **显式声明：仅数据自洽，不重跑实验** |
| **失败时的产出** | 待执行的 `repro_run.sh` + 降级说明 | 翻译产物 + 错误堆栈 | 缺失要素清单 |

## 3.6 关键工程细节

**① 伪代码原语 shim。** 论文伪代码里的 `push(heap,x)`、`empty min-heap`、`sort_descending()`
在 Python 中并不存在。系统在生成代码的骨架里注入了一层薄适配
（约 30 行），把伪代码抽象原语映射到 `heapq` 等实现，
并同时把 `empty min-heap` 这类描述性字面量翻译成 `[]`。
这是"让伪代码真的跑起来"的关键一步。

**② 参数绑定的签名推断。** 伪代码函数签名千变万化（`TOPK(S, k)`、`Normalize(x)`、`Cluster(X, n_clusters)`），
不能盲目 `fn(data)`。系统用**形参名语义**（`k/n/size/window` → 标量；`data/stream/scores/arr` → 序列；
单字母参数 → 序列）绑定实参，失败再退化为位置调用。

**③ 图表重绘的双后端。** 有 `matplotlib` 时输出 PNG + SVG；
没有时自动切到**内置的纯 stdlib SVG 渲染器**，保证"图表重现"环节在任何环境都不空转。
同时内置**量纲守卫**：若一张表里同时有"总请求数 6.3e7"和"命中率 0.83"，
会拒绝出图（画出来只会误导人），并丢弃与主系列差距 100 倍以上的列。

**④ 假阳性防护。** 校验规则全部要求"表头自声明"才触发
（占比列才校验求和、交叉表才校验汇总行、≥3 列才视为交叉表），
避免 `K-Means` 被 `mean` 关键词误判为汇总行、`NMI` 含字母 `n` 被误判为计数列等问题。

## 4.2 PDF 解析 bakeoff（必读）

对样例 `incoming/schnorb_qao_2020`（SchNOrb，arXiv 2005.06979）做了引擎对比（**不发明指标，仅记录实测事实**）：

| 引擎 | 版本/状态 | 结构 | 表格网格 | 公式 | 结论 |
| --- | --- | --- | --- | --- | --- |
| PyMuPDF | 已接线 | 可用（约 7 节） | 弱 | 编号/邻近句可用 | 公式 / 图 / `code_refs` 主力 |
| Docling | **2.126.0** | 强（标题+分节） | **好**（pipe-table） | 弱（`formula-not-decoded` ×34） | 结构/表主力；独立 bakeoff venv |
| Marker | 需 **llama-server** | 有（`--disable_ocr`） | 有 | 全 OCR 被阻 | **不作为默认** |
| MinerU / Nougat | **未装** | — | — | — | 内存/运维成本，不装 |

**选型：hybrid** = Docling 结构（标题 / 章节 / 表格单元格网格）+ PyMuPDF 公式 span / 图路径 / 代码链接。

环境变量：`P2C_PDF_BACKEND=hybrid`（亦支持 `docling` / `pymupdf`）；`P2C_DOCLING_PYTHON` 指向 bakeoff venv，**不**把 Docling/torch 打进 paper2code `.venv`。

**SchNOrb 验收（hybrid 复跑）：**

- 完整标题命中
- **TABLE I** 为 **11×5** 单元格网格
- 公式编号（PyMuPDF 侧）：**1 / 5 / 7 / 12 / 21 / 23** 等
- 仓库模式：**Mode A**（关联 SchNOrb GitHub）
- Docling 首次转换约 ~7 min / ~1.5 GB；有 `paper.docling.md` 缓存后明显快

细节与 P0/P1/P2 改进路线见同目录 **`PDF解析改进方案.md`**。

## 4.3 课件 UX

已落到 `paper2code/explain/courseware.py` 生成的自包含 HTML：

- **宽表**：横向滚动（`overflow-x: auto`）+ **sticky 首列**，避免缩到不可读
- **图/表点击放大**：lightbox 全屏查看；表在放大层仍可横滑
- **幻灯片内滚动**：内容区 `max-height` + 内部滚动，避免溢出 PPT 框
- 底栏提示：`← → 翻页 · 点击图表可放大`

## 4.4 LLM（OpenAI 兼容）

- 协议：OpenAI Compatible（`/v1/chat/completions`）
- Dashboard 预设：**DeepSeek / OpenRouter / SiliconFlow / 自定义**（Base URL + Model）
- Key：**内存粘贴**（重启丢失）或写入 `configs/default.yaml`（**勿 git**）；亦支持环境变量 `P2C_LLM_API_KEY` 等
- 连通性：`POST /api/llm/test`
- 无 Key / 远程失败 → **自动降级 offline**，原因写入产物

## 4.5 上传

Dashboard 本地 file 选择上传（`.pdf` / `.md` / `.html` / `.zip`）→ 保存到 `incoming/uploads/<时间戳>_<文件名>/`，路径自动填入再点「生成」。仍支持手写目录 / 单文件 / arXiv ID。

## 4.6 播客与 TTS

- **文稿**：全中文写作导读 —— 研究目的、思路、方法、结论与不足；**不展开公式与图表**
- **TTS**：SiliconFlow `POST https://api.siliconflow.cn/v1/audio/speech`（OpenAI 兼容）
- **主推模型**：`FunAudioLLM/CosyVoice2-0.5B`（单人）、`fnlp/MOSS-TTSD-v0.5`（双人 `[S1]`/`[S2]`）
- Dashboard「TTS」面板 Key 与 LLM Key 分离；无 TTS Key 时 **edge-tts** 兜底
- 模型表与音色约定见同目录 **`SiliconFlow-TTS模型.md`**

> 本文件不含任何 API Key。
